## Key design decisions (Leiden)

**Two-phase iterative refinement.**
Each iteration has two phases:
- **`fastmove_nodes`**: Deterministic greedy local optimization. Nodes are shuffled and each node is moved to the neighbouring cluster that maximizes gain (or a new empty cluster). Neighbouring clusters are only those adjacent to the node in the graph, reducing the search space.
- **`merge_nodes`**: Probabilistic refinement within each cluster. Singleton clusters are dissolved, and nodes are probabilistically reassigned based on exponential likelihood weighting (scaled by the `beta` temperature parameter). This prevents premature convergence and finds better local optima.

**Hierarchical multi-level aggregation.**
After each iteration, clusters are aggregated into a coarser graph (super-nodes represent clusters). The algorithm repeats on the coarse graph. This multi-scale approach reduces computational cost and improves solution quality. The process continues until the partition stabilizes (no changes) or the number of clusters equals the number of nodes.

**Scratch buffer allocation for hot loops.**
Performance-critical loops (`fastmove_nodes`, `merge_nodes`, `aggregate`) pre-allocate all scratch buffers:
- `weight_to_cluster`: cumulative edge weights from a node to each neighbouring cluster.
- `is_neighbor_cluster`: `FixedBitSet` for O(1) membership checks (avoid repeated vector searches).
- `neighbor_clusters`: reusable vector of candidate cluster indices.
- Buffers are cleared and reused each iteration, avoiding allocation churn.

**Compact CSR graph representation.**
Graphs are stored in Compressed Sparse Row (CSR) format: `offsets` array (row pointers) + `adj` array (neighbor, weight pairs). This is memory-efficient for sparse graphs and enables cache-friendly sequential access. Self-loops are handled specially: counted once (not twice) when building adjacency lists.

**Deterministic subgraph extraction.**
`CsrGraph::subgraph(nodes: &[usize])` builds the induced subgraph on `nodes`, reindexing to contiguous ids in the order of the provided `nodes`. Returns the subgraph plus a `BTreeMap<usize, u32>` from old id to new id; `BTreeMap` keeps the mapping's iteration order reproducible.

**Two objective functions with different semantics.**
- **Modularity** (`LeidenObjective::Modularity`): Weighted by node strengths (sum of incident edge weights). Resolution parameter is normalized by total graph strength. Suitable for detecting communities in networks with heterogeneous node degrees.
- **CPM** (`LeidenObjective::CPM`, Constant Potts Model): All nodes have unit weight. Resolution is absolute. Simpler semantics, useful for uniform community detection.

**Probabilistic refinement via exponential likelihood weighting.**
In `merge_nodes`, cluster choices are weighted by `exp(diff / beta)`, where `diff` is the modularity (or CPM) gain and `beta` is a temperature parameter. High `beta` makes the choice more uniform; low `beta` favors the best cluster. This stochasticity helps escape local optima.

**Cluster ID reindexing and compaction.**
After `fastmove_nodes` and `merge_nodes`, cluster IDs are reindexed to [0..k) to ensure dense numbering (no gaps). This simplifies downstream aggregation and memory use.

**`self.membership` is only ever written by the flatten step in `find_partition`.**
It must be written at *every* level where the loop continues (`continue_clustering`), including level 0. Reference implementations (e.g. igraph's C `community_leiden`) alias their output `membership` pointer directly onto the level-0 working buffer, so `fastmove_vertices`'s in-place writes are automatically visible with no copy needed -- that's why they can special-case level 0 as a no-op. This port instead clones `self.membership` into `aggregated_membership` up front, so level 0's result has no other path back to `self.membership`; skipping that write (as a naive line-for-line port of the C guard would) silently discards the whole clustering whenever the hierarchy happens to converge in exactly two levels. Level 0's copy is a plain `copy_from_slice` rather than the general indexed gather used for level > 0, since `super_node_map` is still the identity mapping at that point in the loop -- if that ordering ever changes, this shortcut needs revisiting.

**`fastmove_nodes`'s stay-in-place baseline must use the same penalized diff formula as every candidate cluster.**
The gain formula is `diff = E(v, C) - resolution * node_weight(v) * cluster_weight(C)`. The initial `max_diff` (representing "leave `v` in `current_cluster`") has to be computed with that same formula applied to `current_cluster`, exactly like every other candidate in the `neighbor_clusters` loop -- matching igraph's `leiden_fastmove_vertices`, which computes its pre-loop baseline the identical way (`leiden.c`, "Calculate maximum diff"). Using the raw, un-penalized `weight_to_cluster[current_cluster]` as the baseline (as an earlier version of this code did) gives staying put a discount no other candidate gets, biasing the local search toward staying in worse clusters. The effect isn't visible on trivial/well-separated graphs (any real improvement clears the inflated bar anyway) but shows up as a measurable, consistent quality gap on anything with real optimization difficulty -- caught by comparing achieved objective values (not partition identity) against igraph over repeated runs, see `pytests/test_leiden_accuracy.py`.

**`leidenp.rs` is a parallel fork of `leiden.rs`, kept algorithmically identical except where noted below.**
`leiden.rs` is the sequential reference implementation and is never modified as part of the parallelization work; `leidenp.rs` (`fast_find_communities`) is being incrementally rewritten phase-by-phase to use `rayon`, capped at 8 threads via a dedicated `rayon::ThreadPool` built once in `fast_find_communities` and stored on `LeidenState`. Progress so far:

- **`merge_nodes` -- parallelized.** Clusters partition the node set, so each cluster's local refinement is independent and runs concurrently via `cluster_scratch.par_iter_mut()`. Two things needed redesigning versus the sequential version: (1) all per-call scratch (`cluster_weights`, `cluster_out_weight`, `weight_to_cluster`, two `FixedBitSet`s, `neighbor_clusters`, `cum_likelihood`, the refined-membership compaction buffer) is now one per-thread `thread_local!` struct (`MergeScratch`), grown-never-shrunk to the largest cluster seen by that thread -- calling this 270M+ times at production scale (mostly for tiny/singleton clusters) made fresh-allocating ~8 buffers per call a real, measured cost; `cluster_weights`/`cluster_out_weight` are freshly written (not reset) on first touch each call since every index in `[0,n)` is touched exactly once, while the two sentinel-pattern buffers (`non_singleton_cluster`, the compaction buffer) track their own touched indices and self-clean just those, avoiding a full-buffer reset; (2) each cluster now returns its own locally-compacted refined ids ([0, k_i)) instead of writing directly into a globally-offset shared counter, since threading one running offset through concurrent calls isn't possible -- a cheap sequential prefix-sum over the per-cluster counts afterward reconciles these into one globally-contiguous id range. This is the only serial part of the phase. **Task granularity note**: most original clusters are tiny/singleton at production scale, so dispatching one rayon task per cluster makes per-task overhead dominate the real (sub-microsecond) work. `.with_min_len(merge_min_len)` batches consecutive clusters into fewer tasks; `merge_min_len` is computed per call as `(nb_clusters / (MAX_THREADS * 4)).clamp(1, MERGE_TASK_MAX_BATCH)`, not passed as the fixed cap directly -- rayon's splitter only splits a range while `len/2 >= min_len`, so a fixed large `min_len` would fully serialize any level with too few clusters (caught by review before shipping; see `LEIDEN_IMPROVEMENTS.md` for the two bigger vertex-centric redesigns that were tried first, both measurably regressed wall time, and were reverted in favour of this smaller, zero-semantic-risk fix). **Known unsolved limitation**: cluster sizes are extremely skewed and correlated with cluster id, so a handful of `with_min_len` batches containing an outsized share of large clusters become multi-second stragglers running alone on 1-2 threads late in the phase; two fixes (LPT-style reordering, random-shuffle dispatch order) were tried and both regressed wall time overall by disturbing cache locality in downstream phases -- see `LEIDEN_IMPROVEMENTS.md` for details. Reverted; not solved.
- **`aggregate` -- parallelized.** Each super-node `c`'s work (scan its members' edges, sum weight to neighbouring super-nodes, pick a representative) is independent across `c` and runs concurrently via `refined_clusters.par_iter()`. Same shared-scratch problem as `merge_nodes`: `weight_to_cluster`/`is_neighbor_cluster`/`neighbor_clusters` (sized to the *new*, coarser graph's node count) become a per-thread `thread_local!` (`AGGREGATE_SCRATCH`), reused across calls and lazily grown (never shrunk) -- `neighbor_clusters` is explicitly `.clear()`'d at the end of each call since it's no longer freshly allocated. Each cluster returns its own local edge list instead of appending to one shared `aggregated_edges`; concatenated by a cheap sequential pass afterward (order-preserving, so the result matches the sequential version's edge order exactly, not just its edge set).
- **`fastmove_nodes` -- parallelized, with a different design than the other two phases.** `merge_nodes`/`aggregate` stay data-parallel over already-disjoint work with a small serial reconciliation pass at the end; that shape doesn't work here because the natural per-node reconciliation is O(n), not O(clusters) -- an earlier attempt at a frozen-snapshot-decide-then-serial-apply design (mirroring the other two phases) hit real, measured problems: batched decisions caused genuine oscillation (neighbours swapping into each other's clusters based on stale data), and the serial reconciliation pass's O(n) cost meant it was *slower* than the sequential version at production scale (confirmed via `top -H`: only 1 of 8 threads ever busy). What's implemented instead follows two published, benchmarked reference implementations (NetworKit's PLM; the GVE-Leiden paper/implementation, arxiv.org/abs/2312.13936, github.com/puzzlef/leiden-communities-openmp): a **fused** parallel decide+apply with no separate phases at all. Every node is swept in parallel each round; each thread scans its own node's neighbours, decides the best move, and commits it immediately via atomics (`membership`/`cluster_weights` become `Vec<AtomicU32>` for the call's duration, `Ordering::Relaxed` throughout). Which nodes need reconsidering each round is tracked via an explicit, shrinking `active: Vec<u32>` work list (round 1: everyone; later rounds: whoever a mover's neighbour-scan queued), not a full per-round scan checking a per-node flag -- on the production dataset's first level this loop runs ~40 rounds, so scanning all `graph.n` nodes every round meant ~40x more index checks than nodes actually needing reconsideration past the first couple of rounds, a real, measured cost. Dedup uses `queued_for: Vec<AtomicU32>` (the round number a node is queued for) rather than a plain boolean cleared at the start of a node's own processing -- an earlier version tried the boolean and it raced a concurrent neighbour's mark of that same node (both active the same round), risking two concurrent `decide_move`/apply calls for one node; the round-number stamp dedupes without needing any reset pass between rounds at all, since each round's stamp is distinct and ever-increasing. Newly-affected neighbours are pushed into a per-thread accumulator (`FASTMOVE_NEXT_ACTIVE`), drained via `ThreadPool::broadcast` after each round -- not `.map(..).collect::<Vec<Vec<u32>>>()`, which was tried first and materializes one (mostly-empty) `Vec` header per *processed* node rather than per node actually queued (~1.2GB of headers for round 1 alone at 50M nodes), cancelling the whole optimization's benefit. `MAX_FASTMOVE_ROUNDS` still caps the loop -- both references cap their own move phase the same way, confirming this is standard practice for the technique, not a hack. One detail neither reference needed: "become a new singleton cluster" is handled by reserving `graph.n + v` as node `v`'s own private, collision-free cluster id, avoiding the need for a shared/serial id allocator -- cluster ids in this function range over `[0, 2*graph.n)`, not `[0, graph.n)`.

All three phases are now parallelized. See `LEIDEN_IMPROVEMENTS.md` (repo root) for the full history and benchmark results.

**`gveleiden.rs` is a from-scratch port of GVE-Leiden (arxiv.org/abs/2312.13936, github.com/puzzlef/leiden-communities-openmp, `inc/leiden.hxx`), not an incremental parallelization of `leiden.rs` like `leidenp.rs` is.** Its public surface mirrors `leidenp.rs` (`gve_find_communities`, a `LeidenState::find_partition` method), but the algorithm inside is genuinely different in three ways straight from the reference, each chosen because it changes *how much work the algorithm does*, not just how it's scheduled:
- **`local_move` stops on a tolerance, not a fixed point.** Each round's total gain is compared against a threshold that shrinks geometrically every aggregation level; the round loop breaks once a round's gain drops below it (capped at `max_iterations` regardless). Uses the same fused parallel decide+apply design as `leidenp.rs::fastmove_nodes` (`vaff`-gated full sweep each round, mirroring the reference's `schedule(dynamic, 2048)`) -- an explicit shrinking active-list (`leidenp.rs::fastmove_nodes`'s own fix) was tried here too and measured *slower*: tolerance-capping already limits this to ~12-13 rounds on the production dataset (vs. ~40 for `fastmove_nodes`'s run-to-fixed-point design), so the wasted per-round scan was never dominant here, and the active-list's extra bookkeeping cost more than it saved. Reverted.
- **Refinement (`refine`) is a single deterministic sweep, not a per-cluster probabilistic search.** Every node starts as its own singleton "refined" community; one parallel pass lets each node try to merge into its best same-local-move-community neighbour, using an atomic `fetch_update` CAS so a community can be joined by at most one winner even under concurrent attempts. No shuffle-per-cluster, no RNG, no `exp(diff/beta)` likelihood weighting -- `beta` doesn't exist in this port's public API.
- **Aggregation stops early once compression stalls** (`aggregation_tolerance`, default 0.8 from the reference): if refined cluster count is already close to the current level's node count, the level loop breaks instead of aggregating further. On this project's production benchmark this needed retuning well above the reference's own default -- 0.8 cut off 3-4 levels that still contributed real quality (H dropped ~6%, internal edge weight 90% vs. the reference's 97%); 0.995 recovers full quality at a modest speed cost. Left at 0.995, not 0.8.

`community_vertices` replaces `leidenp.rs::retrieve_clusters`'s sequential per-node `push` bucketing (explicitly flagged there as an unaddressed bottleneck) with a parallel counting sort: a parallel per-community atomic count, a sequential O(communities) exclusive scan, then a parallel scatter using per-community atomic cursors into disjoint slots of one shared buffer (safe via a `SendPtr` wrapper, same pattern as `leidenp.rs`'s reverted permutation experiment, but load-bearing here rather than reverted). Refinement itself needs no per-cluster enumeration at all (unlike `merge_nodes`), so this counting sort runs once per level, not twice.

Two real, non-obvious bugs were caught porting this, both worth knowing if touching this file again:
- **The "stay in place" baseline must be scored with the same formula as every candidate community**, including excluding `v`'s own weight from its current community's weight -- an implicit `0.0` baseline (as if staying were always as cheap as an empty community) systematically biases toward moving even when staying is better, since the weight to one's own current community is usually positive. This is the exact same bug already documented above for `leidenp.rs::fastmove_nodes`; it recurred here because GVE's own reference expresses the comparison as a true delta (with a `-vdout` term baked in), and porting it as an independent per-candidate score (this file's approach, for consistency with the rest of the codebase's objective handling) silently drops that term unless the baseline is computed the same way as every other candidate.
- **Both `local_move` and `refine` shuffle their processing order before each call, not just once at startup.** This project's RGP-generated graphs frequently have node ids correlated with similarity/generation order; processing in raw ascending order (as GVE's own reference does, via `schedule(dynamic, 2048)` over `0..S`) gives each thread an internally over-similar chunk, causing systematic within-chunk over-merging before any cross-chunk information exchange. Confirmed empirically: quality only matched the sequential reference (community count and objective value) once this was shuffled -- unshuffled, the toy dataset converged to ~40% fewer, much larger communities with visibly worse internal cohesion.

Validated on the toy dataset (community count and objective value within the same variance band as `leiden.rs`/`leidenp.rs`) and the production dataset (objective value and internal-edge-weight fraction matching `leidenp.rs` within noise). Production benchmark: ~3.3x vs. the 175.971s sequential baseline (~52s), ahead of `leidenp.rs`'s 2.74x but short of the GVE paper's own reported 8-thread figure (5.1x vs. their own sequential implementation, a different, cheaper baseline than this repo's `leiden.rs` -- not directly comparable, see below).

**`CsrGraph::new_par`** (`csr_graph.rs`) is a parallel counting-sort equivalent of `new`, added because `aggregate`'s per-level graph rebuild (`new`'s two O(edges) sequential passes, plus the sequential edge-list concatenation feeding it) measured as a real cost at production scale (~1s combined at level 0 alone, out of that level's ~1.2s `aggregate` call). Also fixes a precision bug `new` still has: `new`'s `m` sums directly into an `f32` accumulator, which silently saturates (confirmed: read back as an exact power of two, nowhere near the true value) once the running sum's magnitude exceeds what a single further increment can represent in `f32` -- `new_par` accumulates in `f64` and casts down once at the end. Every buffer this and `community_vertices`/`aggregate`'s scatter-based construction touch is built via `Vec::with_capacity` + `set_len` rather than a value-filled `vec![default; n]`, specifically because filling with a default value only for the immediately-following parallel scatter to overwrite every element doubles the memory traffic for zero benefit -- caught by measuring, not by inspection (the code read as correct either way; only the timing showed the redundant pass).

**Full sequential-time audit, run after the above fixes** (requested explicitly, to answer "what's left to parallelize" precisely rather than by inspection): every remaining single-threaded loop across `find_partition`/`community_vertices`/`aggregate`/`new_par` is now wrapped in a `STAT_SEQ_*`/`STAT_NEWPAR_SCAN` `LockStat` (`#[cfg(feature = "monitor")]`, same convention as the phase timers). Measured total: **3.78s of 51.4s wall time is sequential (7.3%)**, broken down as `reindex_membership` (2.07s, 55% of the sequential total -- called after every `local_move`/`refine`, has a genuine serial dependency through its `next_id` counter, not a quick fix), `find_partition`'s per-restart setup clone (0.86s), the small O(communities) exclusive scans in `community_vertices`/`aggregate` (0.44s), and `new_par`'s own O(n) exclusive scan (0.41s). By Amdahl's law this puts a hard ceiling on how much more speedup chasing sequential bottlenecks alone can buy: eliminating *all* of it entirely would only reach ~1.08x further (1/(1-0.073)). The other 92.7% of wall time is already genuinely parallel work -- so the gap to a higher multiplier is a question of how efficiently that parallel work scales across 8 threads (memory bandwidth saturation from scattered atomic access into large arrays, cache locality) rather than unparallelized code. Confirmed this isn't just theoretical: applying the `new_par`/`set_len` fixes above (removing a real, measured ~1s/level sequential cost) did not move the overall wall-clock number outside run-to-run noise.

**Thread-scaling measurement, to pin down the "not unparallelized code" claim above with data instead of leaving it as an inference.** The production machine (13th Gen Intel Core i7-13700K) is a hybrid design: 8 P-cores with hyperthreading (`lscpu -e` CPUs 0-15, in SMT pairs) plus 8 E-cores without it (CPUs 16-23, ~20% lower clock and meaningfully lower IPC), all on a single NUMA node. Sampling actual thread placement during a run (`ps -T -o tid,psr,pcpu`) across several points in the run showed the 8 rayon workers consistently landed on 8 *distinct* P-cores, not paired on SMT siblings or spilled onto E-cores -- so naive hybrid-scheduling placement isn't the dominant effect. Worker `%CPU` sat at 74-90% throughout, never near 100%, and the main thread's cumulative `%CPU` fell over the course of a run (consistent with it parking during `pool.install()` calls and only being active for the ~7.3% sequential portion plus the pre-Leiden `CsrGraph` load). To isolate genuine parallel efficiency, `find_partition` was run once (`n_iterations=1`, single pass, no perf-counter access available -- `perf_event_paranoid=4`, no sudo) at 1/2/4/8 threads (temporarily via an env-var override, reverted after): **112.5s / 67.3s / 44.1s / 32.7s** -- speedups of 1.67x / 2.55x / 3.45x over the 1-thread baseline, i.e. parallel *efficiency* of 84% / 64% / 43%. Efficiency degrades smoothly starting from the very first doubling (1→2 threads, both trivially fitting on distinct P-cores with no hybrid-core or SMT involvement at all) rather than dropping off a cliff specifically at higher thread counts -- that shape is the signature of a shared-resource bottleneck (memory bandwidth and/or cache-coherency traffic from the many concurrent atomic read-modify-writes into `cluster_weight`/`membership_atomic`/`ctot`, which are accessed at essentially random large-array offsets driven by graph topology), not an OS-scheduling or hybrid-core artifact. Backing the known 7.3% sequential fraction out of the 8-thread number gives ~53% efficiency for the genuinely-parallel portion alone -- meaningfully below what Amdahl's law alone would predict as achievable (a further, real parallel-scaling ceiling on top of the sequential-time one, not explained by it).

**Direct comparison against the actual GVE-Leiden C++ reference, run on this exact graph.** The "memory bandwidth" framing above turned out to be a partially wrong diagnosis -- the reference implementation was cloned (github.com/puzzlef/leiden-communities-openmp), compiled (`g++ -DMAX_THREADS=8 -O3 -fopenmp -std=c++17`), and run on this project's production graph exported to Matrix Market format (via a one-off `bin_export_mtx` binary, using the exact same post-`INWeightType::SimilarityComplement` weights `neighbors()` returns, so it's the identical weighted graph our own algorithm sees). Its own default config (`resolution=1`, `aggregationTolerance=0.8`, matching modularity) converged in 3 passes at **15.735s total** (locmove=8.78s, refine=3.27s, aggr=2.96s) on this hardware -- so the "5.1x on 8 threads vs. their own sequential" figure from the paper is achievable *on this exact machine*, not just in their own benchmark environment. This directly disproved the "our hardware is just slower" hypothesis and pointed at real, fixable inefficiency in this port.

Running our own port with matching config (`aggregation_tolerance=0.8`, `Modularity` objective, `resolution=1`) on the identical graph, to make the level/pass count match (3 each, for a true apples-to-apples per-phase comparison rather than comparing totals across runs that did different amounts of algorithmic work), found and fixed three real inefficiencies:

1. **`local_move`'s per-round "already inactive?" check used `AtomicBool::swap`, not `load`.** On x86 a relaxed atomic load compiles to a plain `mov` (free), but `swap` always needs a `LOCK XCHG` (cache-line-owning, expensive under any contention) regardless of whether the value even changes. The reference's own skip-check is a plain, non-atomic `vector<char>` read -- it never pays this cost at all. Later rounds have a shrinking active fraction (most of the `n` checks are misses), so paying `LOCK XCHG` for every one of them, not just genuinely active nodes, was real, unnecessary cross-core traffic. Fixed with a cheap `load` before the `swap` that actually claims the flag -- 12% faster on `local_move` alone.
2. **The Fisher-Yates shuffle needed for id-decorrelation (see the two bugs documented above) is inherently sequential** and measured as a real cost (~570ms at n=50M, paid at least twice per level). Replaced with sorting by a cheap 64-bit hash of each index (`scramble`, murmur3's `fmix64` finalizer) -- fully parallel via `par_sort_unstable_by_key`, and still provably visits every index exactly once (a sort of the same `[0, n)` set can't skip or duplicate an element, unlike a formula-based permutation). Confirmed to produce the same quality (toy dataset community count/objective unchanged).
3. **No release-profile tuning at all** (`codegen-units=16` default, no LTO) -- unlike the reference, which is one translation unit under `g++ -O3` and gets full cross-function inlining for free. Added `[profile.release] lto = true, codegen-units = 1` to the workspace root `Cargo.toml` (panic strategy left untouched, since pyo3's FFI boundary relies on unwinding). ~6% faster across the board.

A fourth attempt -- replacing `aggregate`'s per-community `Vec::new()` (tens of millions of tiny allocations at level 0, the same anti-pattern already fixed in `leidenp.rs::merge_nodes`) with a `SmallVec` to avoid heap allocation for the common small case -- was tried and reverted: it measured *slower*, not faster, because `SmallVec`'s larger inline struct size (48 bytes vs `Vec`'s 24) increased the memory footprint of the tens-of-millions-of-entries `results` collection more than it saved, especially since `mimalloc` (already the global allocator, per `bench_leiden.rs`) is specifically optimized for cheap small/frequent allocations. A worthwhile lesson: the same fix that was a real win in one call site (`merge_nodes`, called 270M+ times) was a net loss in a structurally-similar-looking one, because the actual bottleneck (allocation cost vs. struct-size/cache-footprint) differs by call site and has to be measured, not inferred from the pattern matching a previous fix.

Net effect of all three real fixes together, same matched-config (3-pass) comparison: **28.5s -> 24.6s**, narrowing the gap to the reference from 2.11x to **1.56x** slower. `aggregate`'s per-community dispatch was profiled further (splitting `community_vertices`/dispatch/tail, and testing a larger rayon batch size, which made no difference -- ruling out dispatch overhead) but its remaining ~2x-per-edge cost versus the reference's `aggr` timing couldn't be pinned down further without hardware performance counters (`perf_event_paranoid=4` blocks `perf stat` in this environment, no sudo access to lower it). That's the concrete next step if this gap needs closing further: get `perf stat` (IPC, cache-miss rate) access to distinguish memory-bandwidth-bound from cache-coherency-bound from something still-fixable in the code, rather than guessing further. Production benchmark (this project's actual CPM/low-γ workload, `aggregation_tolerance=0.995`) improved from ~50-53s to **44.1s** (3.99x vs. the 175.971s sequential baseline) from this round's fixes.
